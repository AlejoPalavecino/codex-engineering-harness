# Chuli v0.2.1 — candidata de mantenimiento

> Estado: candidata en revisión. Esta nota describe el contenido propuesto; no implica que exista una release ni binarios publicados.

## Objetivo

Corregir tres fallos reproducibles de v0.2.0: pérdida del inventario administrado después de una reinstalación sin cambios, verificación exitosa con recursos obligatorios ausentes y selección de ejecutores de rollback incompatibles desde checkouts antiguos.

## Cambios

### Instalación y actualización

- El manifiesto incorpora `managed_files`, separado de `files`: el primero conserva el hash oficial de cada recurso; el segundo contiene solo operaciones que requieren backup para rollback.
- Una reinstalación sin cambios mantiene los 13 hashes administrados aunque `files` quede vacío.
- Los manifiestos históricos v0.1.3 y v0.2.0 se migran mediante baselines SHA-256 versionados en `scripts/legacy-managed-hashes.json`.
- Los recursos que coinciden con su hash oficial histórico se actualizan; los archivos distintos siguen tratándose como personalizaciones y no se sobrescriben sin `-ReplaceCustomized`.

### Verificación

- `verify.ps1` comprueba presencia e integridad conocida de instrucciones globales, cuatro agentes, cinco skills y tres recursos TTP.
- La ausencia de cualquiera de los 13 recursos obligatorios incrementa los errores y devuelve código de salida 1.
- La deriva de hash se informa como advertencia; la verificación no modifica archivos.

### Rollback y Manager

- El manifiesto registra `schema_version` y `rollback_schema_version`.
- El rollback valida la versión mínima del ejecutor, el esquema, la estructura de ambos manifiestos, rutas relativas, duplicados y backups antes de restaurar.
- El JSON anterior debe poder parsearse y contener una estructura válida antes de tocar los archivos.
- Chuli Manager rechaza checkouts anteriores a v0.2.1 para rollback. El script también comprueba la versión mínima, incluso si se invoca directamente.
- Los estados sin `rollback_schema_version` se interpretan como esquema 1; el ejecutor v0.2.1 admite esquemas 1 y 2.

## Regresiones añadidas

- Reinstalación idempotente con inventario persistente.
- Migración desde un manifiesto v0.2.0 con `files: []`, usando un fixture byte-exact y su SHA-256 histórico.
- Verificación con un recurso obligatorio ausente y comprobación de que no modifica el home.
- Rollback con backup faltante, comprobando que no restaura parcialmente.
- Rollback con JSON anterior corrupto, comprobando que no escribe.
- Tests Go para rechazar ejecutores locales anteriores a v0.2.1 y esquemas desconocidos.
- Ejecución Windows en PowerShell 7 y Windows PowerShell 5.1.

## Alcance y límites

- La migración histórica cubre v0.1.3 y v0.2.0. Una versión futura que cambie recursos instalados deberá agregar sus hashes históricos antes de retirar el estado anterior.
- Instalación y rollback continúan habilitados solo en Windows.
- El verificador confirma recursos y deriva local; no certifica modelos ejecutados, autenticidad de evidencias, permisos efectivos de Codex ni aislamiento de subagentes.
- Esta candidata no agrega agentes, MCP, proveedores ni comportamiento de evaluación.

## Criterio para publicar

Publicar solo después de que el CI de la rama y el PR pase completo, incluyendo los dos motores de PowerShell. Repetir una instalación v0.2.0 con inventario vacío, verificar que el archivo oficial se actualiza y que una personalización distinta se preserva. Confirmar que el rollback falla sin cambios ante backups faltantes y manifiestos corruptos. La publicación debe apuntar al SHA exacto integrado en `main`.
